# 04. RAG構築ガイドと月額の見積り（3,000円以内）

Word資料を根拠に、賢く答えを引き出す仕組み（RAG）を足す話です。結論を先に書きます。

- **費用は問題になりません。** 内部テスト規模なら、AIを使っても月額は数十〜数百円で収まり、3,000円は余裕で守れます。**縛りになるのはお金ではなく「安全性・監修」です。**
- このアプリは**性暴力・DV・体調**を、**10代を含む利用者**が使います。AIに自由に文章を作らせると、誤った助言・危険な言い回しが混じるリスクがあります。そこで **「取り出し（retrieval）は賢く、表示する文章は監修済み」** を基本にし、生成は限定的に使う設計を薦めます。
- そのため RAG を**3段階**に分け、**下の段から順に**導入するのが安全です。

---

## RAG とは（このアプリでの意味）

RAG ＝「①資料から関連部分を**取り出し**て、②それを**根拠**に答える」仕組みです。実はこのアプリの現状（キーワードで該当テーマを引く）も、①の素朴版です。改善の余地があるのは主に **①の精度** と、**②を監修文にとどめるか／AIに書かせるか** の2点です。

---

## 段階0：キーワード検索（いまの方式）― 費用 ¥0

`knowledge.json` の `keywords` に一致するテーマを返します。**表示は必ず監修文**なので最も安全。GitHub Pages だけで動きます。

**弱点（実例）**：テスト中、「家族から暴力をうけている」が DV に当たらず取りこぼしました（`keywords` に一般語「暴力」「家族」が無かったため）。→ 語を足して解決しましたが、**言い換えを人手で網羅し続ける**必要があります。これが次の段の動機です。

---

## 段階1：意味検索（埋め込み）で取り出しを賢く ― 表示は監修文のまま ― 費用 ほぼ¥0【推奨】

**「取り出し」だけをAIで賢くし、返す文章は段階0と同じ監修済み文**にします。10代・繊細な話題に対して、**表示される言葉が全部監修済み**という安全性を保ったまま、取りこぼしを大きく減らせます。

仕組み：
1. Word資料を短い塊（＝`chunks`）に分け、各塊を**埋め込み（embedding）＝意味のベクトル**に変換して `vectors.json` に保存（オフラインで1回だけ）。
2. 利用者の入力も埋め込みに変換し、**意味が近い塊**を選ぶ（キーワード一致より賢い）。
3. 選ばれた塊に対応する**監修済みの empathy／steps／窓口**を返す。**AIは文章を書きません。**

**費用**：埋め込みは激安（後述）。しかも塊が数十〜数百件なら、**近さの計算はブラウザ内でできる**ので、資料の索引作成を1回だけAPIで行えば、あとは実質API不要にもできます。→ **月額はほぼ¥0**。

> まずはここまでを目標にするのを薦めます。安全性を落とさずに賢くなります。

---

## 段階2：中継サーバー＋LLMで文章を生成（方式C）― 費用も3,000円以内

想定外の相談（「そのほか」に落ちるもの）にも文章で応じたい場合の最終段。**方式C＝キーを隠す中継サーバー**が前提です（画面にキーを置く方式Bは採用しません）。

構成：

```
[利用者] → GitHub Pages(index.html)
              │  ①入力を中継サーバーへ
              ▼
        [中継サーバー] Cloudflare Workers / Vercel（無料枠・キーはここに保管）
              │  ②入力を埋め込み → 近いchunkを取り出し（RAG）
              │  ③「取り出したchunkだけを根拠に、監修トーンで」LLMに書かせる
              ▼
        [LLM API]（gpt-4o-mini / Gemini Flash / Claude Haiku など安価モデル）
```

**安全のための必須ガード**（システムプロンプト側で固定）：
- 取り出した根拠の**外の情報を作らない**（「資料にない事柄は述べない」）。
- **危機的な内容（自傷・被害進行中・命の危険）は生成せず**、監修済みの緊急文＋窓口に**必ずフォールバック**。
- 回答末尾に**相談先を常に表示**（緊急連絡先が画面から消えない原則を維持）。
- 生成した回答は**ログに残し、運営が事後レビュー**できるようにする（`docs/03` の仕組みを流用）。

> 生成を入れるなら、**緊急テーマは段階0/1の監修文で確定**させ、AIは**非緊急の「そのほか」だけ**に限定するのが安全です。

## 月額の見積り（なぜ3,000円で足りるのか）

内訳ごとに、内部テスト規模（1か月に数百セッション程度）で見積もります。

| 項目 | 使うもの | 月額の目安 |
|---|---|---|
| ホスティング | GitHub Pages | **¥0** |
| 中継サーバー | Cloudflare Workers 無料枠（10万リクエスト/日）または Vercel Hobby | **¥0** |
| ベクトル保管 | `vectors.json`（塊が数百件までなら十分）／必要なら Cloudflare Vectorize・Supabase の無料枠 | **¥0** |
| 埋め込み（索引作成・1回） | 例：OpenAI `text-embedding-3-small`（約 $0.02 / 100万トークン） | **数円**（一度きり） |
| 埋め込み（入力ごと） | 1回あたり数十〜百トークン | **1回 ¥0.01 未満** |
| 生成（段階2のみ） | gpt-4o-mini 等の安価モデル。1回 ≒ 入力2千＋出力4百トークン | **1回 ¥0.1〜0.3 程度** |

ざっくり：**段階1まで＝ほぼ¥0**。**段階2で生成を入れても**、1回¥0.1〜0.3 なら **3,000円 ÷ 0.3 ≒ 1万回/月** まで賄えます。内部テストでこの回数には届きません。

### 予算を“絶対に”超えないための設定（重要）

見積り上は余裕でも、暴走ループなどの事故に備えて**上限を機械的にかけて**ください。

- **APIダッシュボードで月額ハードキャップ**を設定（例：$20 で停止）。OpenAI・Anthropic・Google いずれも上限/アラート設定があります。
- **中継サーバー側でレート制限**（同一IP・単位時間あたりの回数上限）。
- **入力・出力の最大トークンを固定**（長文で費用が伸びるのを防ぐ）。

### 日本語の注意（見積りの精度）

日本語は英語よりトークン数が1.5〜2倍ほど増えます。それでも上の桁数（1回コンマ数円）は変わりません。

> 価格は改定されます。ここに書いた単価は目安です。**契約前に各社の料金ページで最新値を確認**してください（当方は最新価格を自動取得できません）。

## いちばん予算に優しい単一ベンダー構成（任意）

複数サービスを跨ぎたくない場合、**Cloudflare だけ**でも組めます。**Workers（中継）＋ Workers AI（埋め込み・小型LLM）＋ Vectorize（ベクトルDB）** が1か所に揃い、無料割当があるうえ従量も安価です。運用がシンプルになるので、テスト段階の候補として有力です。

## 参考：最小構成のコード断片（第2段階用・雰囲気の把握に）

**(a) 索引作成（オフラインで1回）― Python**

```python
# pip install openai python-docx
import json
from openai import OpenAI
client = OpenAI()  # APIキーは環境変数から

chunks = json.load(open("knowledge.json"))["chunks"]
out = []
for c in chunks:
    text = f"{c['title']}｜{'／'.join(c['keywords'])}｜{c.get('body','')}"
    v = client.embeddings.create(model="text-embedding-3-small", input=text).data[0].embedding
    out.append({"id": c["id"], "v": v})
json.dump(out, open("vectors.json", "w"))  # ← これを中継サーバーに置く
```

**(b) 中継サーバー（Cloudflare Worker）― キーはここに隠れる**

```js
export default {
  async fetch(req, env) {
    const { text } = await req.json();
    // 1) 入力を埋め込み
    const emb = await fetch("https://api.openai.com/v1/embeddings", {
      method: "POST",
      headers: { "Authorization": `Bearer ${env.OPENAI_KEY}`, "Content-Type": "application/json" },
      body: JSON.stringify({ model: "text-embedding-3-small", input: text })
    }).then(r => r.json());
    const q = emb.data[0].embedding;
    // 2) vectors.json と cos類似度で近いchunkを選ぶ（実装は割愛）
    const topId = nearest(q, env.VECTORS);      // → "period" 等
    // 3) 段階1: そのchunkの監修文をそのまま返す（生成しない＝最も安全）
    return Response.json({ topicId: topId });
    // （段階2で生成を足す場合は、ここで topId のbody等を根拠にLLMを呼ぶ）
  }
}
```

段階1では **(b) の 3) が「監修文を返すだけ」** なので、費用も安全リスクも最小です。生成（段階2）はガードを固めてから、非緊急のみに限定して足してください。

## 進め方のおすすめ

1. **いま**：段階0のままGitHub Pagesで内部テスト。取りこぼしは `keywords` を足して対応（`docs/02`）。
2. **次**：段階1（意味検索＋監修文）を追加。安全性はそのまま、取りこぼしが激減。索引作成の数円だけ。
3. **必要なら**：段階2（生成）を、**非緊急の「そのほか」限定・ハードキャップ付き・ログ事後レビュー付き**で追加。

この順なら、**3,000円/月を守りつつ**、10代が使う窓口としての安全性を落とさずに賢くできます。
